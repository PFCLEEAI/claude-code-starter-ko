    접혀 있는 "더 알아보기"는 궁금할 때만 펼치면 돼요. 안 읽어도 흐름은 이어져요.

    AI 도구 지형도: 뭐가 뭔지 정리하기

    3줄 요약
    • LLM은 엄청난 양의 글을 읽고 "다음에 올 말"을 맞히도록 훈련된 모델이에요.
    • Opus·Sonnet·Haiku는 모델(엔진)이고, Claude 채팅·Claude Code·Cowork는 그 모델을 쓰는 앱(자동차)이에요.
    • 대화로 답을 받고 싶으면 채팅, 내 폴더의 파일을 직접 만들고 고치게 하려면 Claude Code나 Cowork를 써요.

    LLM이 뭐예요?

    LLM(Large Language Model, 대규모 언어 모델)은 인터넷 글, 책, 코드 같은 텍스트를 아주 많이 읽고 학습한 프로그램이에요. 하는 일은 의외로 단순해요. 지금까지 나온 글을 보고 다음에 올 말을 예측하는 거예요.

    이 예측을 한 조각(토큰)씩 계속 이어 붙이면 문장이 되고, 문단이 되고, 기획서가 돼요. 그래서 질문에 답하고, 글을 요약하고, 코드도 쓸 수 있어요.

    비유 휴대폰 키보드의 자동완성을 떠올려 보세요. "오늘 저녁" 다음에 "뭐 먹지"를 추천해 주죠. LLM은 그 자동완성이 책 수백만 권을 읽고 엄청 똑똑해진 버전이라고 생각하면 돼요.
    ⚠️ LLM은 "그럴듯한 말"을 만드는 데 강해요. 그래서 틀린 내용도 자신 있게 말할 때가 있어요(환각, hallucination). 숫자·날짜·출처는 꼭 직접 확인하세요.
    🧪 예시

    상황: 지역 관광 콘텐츠를 준비하면서 Claude 채팅에 문장 앞부분만 넣어 봐요.

    대구 근대골목 투어는

    결과(예시 답변, 실제 문장은 매번 달라요): 질문이 아닌데도 "골목길을 따라 100년 전 대구의 모습을 만나는 도보 코스예요…"처럼 뒷말을 자연스럽게 이어 써요. 이게 "다음 말 예측"이에요. 거기 나온 소요 시간이나 운영 요일은 그럴듯해도 공식 안내에서 꼭 다시 확인하세요.

    모델 vs 앱

    헷갈리기 쉬운 부분이에요. 모델은 실제로 생각하고 글을 만드는 두뇌이고, 앱은 그 두뇌를 우리가 쓸 수 있게 감싼 프로그램이에요.

    비유 모델은 자동차 엔진, 앱은 자동차예요. 같은 엔진을 승용차에도 트럭에도 넣을 수 있죠. Claude 모델 하나를 채팅 앱에도, Claude Code에도 넣어서 쓰는 거예요.

    Opus

    세 가지 중 가장 똑똑한 쪽이에요. 어렵고 긴 작업에 써요. 대신 느리고 사용량을 많이 써요.

    Sonnet

    성능과 속도의 균형이 좋아요. 일상 작업은 대부분 이걸로 충분해요.

    Haiku

    가장 빠르고 가벼워요. 간단한 분류나 요약처럼 빨리 끝낼 일에 맞아요.

    📌 모델 이름 뒤 숫자(버전)는 계속 바뀌어요. Claude Code 안에서는 /model로 지금 쓰는 모델을 확인하고 바꿀 수 있어요. 목록에 이 셋 말고 다른 이름(예: Fable)이 보이면 그것도 모델, 즉 엔진이에요.
    🧪 예시

    상황: 피치덱 전체 구조를 잡는 어려운 작업이라 더 똑똑한 모델로 바꾸고 싶어요. 터미널에서 연 Claude Code 입력창에 이렇게 쳐요.

    /model

    결과: 쓸 수 있는 모델 목록이 떠요. 앱(Claude Code)은 그대로고 엔진만 갈아 끼운 거예요. 리뷰 분류처럼 단순한 일로 돌아오면 다시 가벼운 모델로 바꾸면 돼요. 여기서 고른 모델은 다음 세션 기본값으로도 저장돼요. 이번 세션만 바꾸고 싶으면 목록에서 해당 줄에 s를 누르세요. 데스크톱 앱 Code 탭에서는 /model 대신 전송 버튼 옆 모델 드롭다운에서 고르면 돼요. 세션 중간에도 바꿀 수 있어요.

    Claude 채팅 vs Claude Code vs Cowork vs Claude in Chrome

    모두 같은 Claude지만, 일하는 장소와 손이 닿는 범위가 달라요.

    앱어디서 써요?잘하는 일이럴 때 써요
    Claude.ai 채팅웹 브라우저, 모바일 앱대화로 묻고 답하기, 글쓰기, 아이디어 정리"올리브영 신상 립밤 기획 아이디어 10개 줘"처럼 답만 받으면 될 때
    Claude Code터미널, 데스크톱 앱 Code 탭, 웹(claude.ai/code), VS Code·JetBrains폴더 안 파일을 읽고 만들고 고치기, 명령 실행, 여러 단계 작업리서치 노트 폴더 정리, 웹페이지 만들기, 배포까지 직접 시키고 싶을 때
    CoworkClaude 데스크톱 앱 (macOS·Windows)Claude Code와 같은 방식의 에이전트를 코딩 없이 쓰기. 폴더를 주면 파일을 읽고 만들고 고쳐요다운로드 폴더 정리, 스크린샷으로 스프레드시트 만들기, 메모로 보고서 만들기
    Claude in Chrome크롬 브라우저 확장 프로그램크롬 탭의 내용을 읽고 클릭·입력 같은 동작하기로그인된 사이트에서 정보 모으기, 반복 입력 자동화. Claude Code와 연결해서도 써요
    💡 Cowork는 유료 요금제(Pro·Max·Team·Enterprise)에서 쓸 수 있어요. "코딩 없는 Claude Code"라고 생각하면 이해가 쉬워요.
    📌 Claude in Chrome은 내 브라우저의 로그인 상태를 그대로 써요. 로그인 화면이나 CAPTCHA가 나오면 멈추고 나에게 직접 처리해 달라고 해요.
    🧪 예시

    상황: 올리브영 립밤 리뷰 30개를 모아 둔 reviews.csv를 요약하고 싶어요. 같은 일을 채팅과 Claude Code에 각각 시켜 봐요.

    API: 프로그램끼리 주문하는 창구

    API(Application Programming Interface)는 프로그램이 다른 프로그램에게 일을 부탁하는 정해진 창구예요. 사람은 화면을 클릭하지만, 프로그램은 API로 요청을 보내고 답을 받아요.

    비유 식당을 떠올려 보세요. 손님(내 앱)은 주방에 직접 들어가지 않아요. 메뉴판(API 문서)을 보고 웨이터(API)에게 주문하면, 웨이터가 주방(AI 모델 서버)에 전달하고 완성된 음식(결과)을 가져다줘요.

    부트캠프 후반에 n8n 자동화, Supabase 데이터베이스, 이미지·영상 생성 도구를 연결할 때 API가 계속 나와요. "이 서비스에 API로 연결한다"는 말은 "웨이터를 통해 주문한다"는 뜻이라고 기억하면 돼요.

    🧪 예시

    상황: n8n으로 매일 아침 대구 관광 뉴스 요약을 받는 자동화를 만들어요. n8n이 매일 아침 뉴스 사이트 RSS에서 대구 관광 기사 3개를 가져와요. 그다음 Claude API로 이렇게 주문해요.

    주문: (가져온 기사 3개 본문) + "각각 한 줄씩 요약해 줘" + 내 API 키
돌아온 결과: "1. (첫 번째 뉴스 한 줄 요약) …" 같은 글자 데이터

    결과: 화면을 클릭하는 사람 없이도 n8n이 API로 주문하고, 받은 요약을 메일이나 슬랙으로 넘길 수 있어요.

    API 키 = 비밀번호

    API 키는 "이 주문은 내 계정으로 처리해 주세요"라는 증명서예요. 키를 가진 사람은 누구든 내 이름으로 주문할 수 있고, 요금도 내 계정으로 나가요.

    ⚠️ API 키는 비밀번호예요. 절대 공유하지 마세요.
    • 단톡방, 디스코드, 스크린샷, 발표 슬라이드에 올리지 않기
    • GitHub에 올라가는 파일에 직접 적지 않기 (보통 .env 같은 따로 두는 파일에 보관하고, 그 파일은 GitHub에 올리지 않아요)
    • 실수로 노출됐다면 바로 해당 서비스에서 키를 삭제하고 새로 발급받기
    🧪 예시

    상황: 팀 프로젝트 웹페이지에 이미지 생성 API를 붙이는데, GitHub에도 올려야 해요. Claude Code에 이렇게 부탁해요.

    API 키는 .env 파일에 넣고, .gitignore에 .env를 추가해 줘.
코드에는 키를 직접 적지 말고 .env에서 읽어 오게 해 줘.

    결과: 키는 내 컴퓨터의 .env에만 남고, GitHub에 올라가는 코드에는 키가 안 보여요. 키 값 자체는 대화창에 붙여 넣지 말고 .env 파일을 직접 열어 적는 게 더 안전해요.

    Claude Code 해부도

    가운데에는 Claude 모델이 있어요. 모델은 글을 읽고 생각하고 답을 쓰는 "두뇌"예요. 그런데 두뇌만으로는 파일을 열거나 내 규칙을 기억하지 못해요.

    그래서 Claude Code는 모델 주변에 여러 장치를 붙여요. 이렇게 모델을 감싸서 일 잘하는 에이전트로 만드는 장치 전체를 하네스(harness)라고 불러요.

    비유 모델은 머리 좋은 신입 인턴이에요. CLAUDE.md는 첫날 받는 업무 안내서, 스킬은 서랍 속 매뉴얼, MCP는 노트북의 USB-C 포트(어떤 사내 시스템이든 같은 방식으로 꽂음), 훅은 "문 열리면 불 켜짐" 같은 자동 센서, 서브에이전트는 잠깐 불러 쓰는 동료, 권한 모드는 결재 라인이에요.
    🧪 예시

    상황: 팀 프로젝트 폴더에서 올리브영 비건 선크림 카드뉴스 문구를 부탁해요.

    결과: 요청은 한 줄인데 부품 여러 개가 같이 움직여요. CLAUDE.md의 "해요체로" 규칙을 지키고, 카드뉴스 스킬이 있으면 펼쳐 보고, 파일을 저장하기 직전엔 권한 모드에 따라 "저장해도 될까요?"를 물어요.

    CLAUDE.md: 매번 읽는 안내서

    CLAUDE.md는 평범한 마크다운 파일이에요. Claude Code는 세션을 시작할 때마다 이 파일을 읽고 대화 내내 참고해요.

    "답은 한국어로", "출처 링크는 꼭 달아줘", "노트는 notes 폴더에 저장" 같은 말을 매번 반복하고 있다면 여기 적어 두면 돼요.

    종류위치누구에게 적용이런 걸 적어요
    전역(사용자)~/.claude/CLAUDE.md내 컴퓨터의 모든 프로젝트"항상 해요체로 답해줘" 같은 내 취향
    프로젝트./CLAUDE.md 또는 ./.claude/CLAUDE.md이 폴더에서 일하는 모두 (Git으로 올리면 팀원도 같은 파일을 받아요. 08장 참고)폴더 구조, 저장 규칙, 팀 공통 작업 방식
    로컬./CLAUDE.local.md이 폴더의 나만공유하기 싫은 개인 메모. .gitignore에 추가해요

    중요한 점은 이 파일들이 서로를 덮어쓰지 않고 이어 붙는다는 거예요. 위쪽 폴더부터 지금 폴더 순서로 쌓이고, 지금 폴더에 가까운 내용일수록 나중에 읽혀요. 같은 폴더 안에서는 CLAUDE.local.md가 CLAUDE.md 뒤에 붙어요.

    만드는 법은 두 가지예요.

    1. /init을 입력하면 Claude가 폴더를 살펴보고 시작용 CLAUDE.md를 만들어 줘요. 이미 있으면 덮어쓰지 않고 고칠 점을 제안해요.
    2. /memory를 입력하면 전역·프로젝트·로컬 파일 목록이 뜨고, 골라서 바로 편집할 수 있어요. 아직 없는 파일을 고르면 새로 만들어 줘요.

    잘 읽혔는지는 /context를 입력해서 Memory files 목록에서 확인해요.

    # 대구 로컬 브랜드 리서치

## 이 폴더는
- 대구 로컬 브랜드(카페, 베이커리, 굿즈) 조사 노트를 모으는 곳이에요.

## 규칙
- 답변은 한국어 해요체로 써줘.
- 자료를 인용하면 출처 링크를 꼭 붙여줘.
- 확인되지 않은 수치는 "추정"이라고 표시해줘.
- 새 노트는 notes/브랜드이름.md 로 저장해줘.

## 자주 하는 일
- 브랜드 조사: 창업 연도, 대표 상품, 타깃 고객, 인스타 말투 정리
- 비교표: 브랜드 3곳을 표 하나로 비교
    🧪 예시

    • 프로젝트 스킬: .claude/skills/<스킬이름>/SKILL.md (이 폴더, Git으로 팀 공유)
    • 목록 보기: /skills

    맨 위 --- 두 줄 사이는 이름표예요. name은 / 뒤에 칠 이름, description은 언제 쓰는지 설명이에요. 그 아래가 Claude가 따라 할 본문이에요. 파일은 직접 안 만들어도 돼요. "아래 내용으로 .claude/skills/brand-caption/SKILL.md 만들어줘"라고 Claude에게 부탁하면 돼요.

    ---
name: brand-caption
description: 대구 로컬 카페 브랜드 말투로 인스타 캡션을 쓴다. 캡션, 인스타 문구 요청이 오면 사용.
---

1. 브랜드 말투: 다정한 반말, 이모지 2개 이하
2. 첫 줄에 계절감 있는 한 문장
3. 해시태그 5개 (지역명 1개 포함)
    🧪 예시

    상황: 위 brand-caption 스킬을 저장해 둔 상태예요.

    /brand-caption 신메뉴 대추 라떼 출시

    또는 이렇게 그냥 말해도 돼요.

    이번 주 신메뉴 인스타 캡션 써줘

    결과: 첫 번째처럼 직접 부르면 바로, 두 번째처럼 말하면 Claude가 description을 보고 스스로 스킬을 꺼내요. 어느 쪽이든 다정한 반말, 이모지 2개 이하, 지역명이 든 해시태그 5개로 캡션이 나와요.

    💡 Claude가 자동으로 꺼낼지 말지는 description이 정해요. "언제 쓰는지"까지 적어 주세요. 배포처럼 내가 정한 때만 돌려야 하는 스킬은 disable-model-invocation: true를 넣어 자동 실행을 막아요.

    플러그인(Plugin): 한 번에 설치하는 묶음

    플러그인은 스킬, 서브에이전트, 훅, MCP 서버를 한 상자에 담아 한 번에 설치하는 묶음이에요. 남이 잘 만들어 둔 세팅을 통째로 받아 쓰거나, 내 세팅을 팀원에게 나눠 줄 때 써요.

    플러그인은 마켓플레이스(marketplace)라는 목록에서 골라요. Anthropic 공식 마켓플레이스는 터미널에서 처음 실행할 때 자동으로 추가돼요.

    • 터미널: /plugin을 입력하고 Discover 탭에서 골라 설치해요.
    • 다른 마켓플레이스는 /plugin marketplace add로 추가해요.
    • 데스크톱 앱: 입력창 옆 + 버튼 → Plugins → Add plugin
    🧪 예시

    상황: 브랜드 스킬을 처음 만들어 보는데, 스킬 만들기를 도와주는 세팅을 받아 쓰고 싶어요.

    /plugin install skill-creator@claude-plugins-official

    결과: 공식 마켓플레이스에서 skill-creator 플러그인이 설치돼요. 설치 요약에 바로 켜졌는지, /reload-plugins를 실행해야 하는지 나와요.

    ⚠️ 켜 둔 플러그인은 쓰지 않는 세션에서도 컨텍스트를 조금씩 차지하고, 내 권한으로 실행돼요. 믿을 만한 것만, 필요한 것만 설치하세요.

    MCP: 외부 서비스와 잇는 USB-C

    MCP(Model Context Protocol)는 Claude를 Notion, Gmail, 구글 드라이브, Figma 같은 외부 서비스와 연결하는 공통 규격이에요. MCP 서버를 하나 연결하면 Claude가 그 서비스를 다루는 도구를 새로 얻어요.

    비유 USB-C 포트를 떠올리세요. 노트북에 USB-C 구멍 하나만 있으면 충전기, 모니터, 외장하드를 다 꽂을 수 있죠. MCP도 규격이 하나라서 어떤 서비스든 같은 방식으로 꽂아요.

    데스크톱 앱에서는 입력창 옆 + 버튼 → Connectors에서 Notion, Slack, GitHub 같은 서비스를 클릭으로 연결할 수 있어요(커넥터도 MCP 서버예요). 목록에 없는 서비스만 아래처럼 터미널에서 추가해요.

    터미널 추가는 Claude 입력창 말고 일반 셸에서 이렇게 해요. 공식 문서의 실제 예시예요.

    claude mcp add --transport http notion https://mcp.notion.com/mcp

    연결 상태 확인과 로그인은 Claude 안에서 /mcp로 해요.

    🧪 예시

    상황: Notion MCP를 연결했어요. 관광 콘텐츠 기획 DB는 노션에 있어요.

    노션 "대구 관광 콘텐츠" 데이터베이스에서 이번 주 마감인 항목만 뽑아서 표로 정리해줘

    결과: 노션을 열어 복사해 붙여넣지 않아도 돼요. Claude가 Notion MCP 도구로 직접 읽어 와 표를 만들어요. 권한 모드에 따라 처음엔 그 도구를 써도 되는지 물어봐요.

    더 알아보기: MCP 범위
    범위(scope)어디서 쓰나팀 공유저장 위치
    local (기본값)지금 프로젝트만아니요~/.claude.json
    project지금 프로젝트만예 (Git)프로젝트 루트의 .mcp.json
    user내 모든 프로젝트아니요~/.claude.json

    범위는 --scope project나 --scope user처럼 붙여서 정해요.

    훅(Hook): 특정 순간 자동으로 도는 명령

    훅은 "이 일이 생기면 항상 이 명령을 실행해"라는 규칙이에요. Claude가 판단해서 하는 게 아니라 Claude Code가 기계적으로 실행해서, 빠지는 일이 없어요.

    더 알아보기: 자주 쓰는 훅 이벤트 5가지
    이벤트언제쓰임 예시
    NotificationClaude가 내 입력이나 허락을 기다릴 때데스크톱 알림 띄우기
    PreToolUse도구 실행 직전 (막을 수 있음)중요 파일 수정 막기
    PostToolUse도구 실행 성공 직후파일 고친 뒤 자동 정리
    SessionStart세션 시작·재개 때필요한 맥락 미리 넣기
    StopClaude가 답을 마쳤을 때작업 끝 알림

    이 밖에도 이벤트가 30개 넘게 있어요. 전체 목록은 공식 문서 ↗를 보세요.

    훅은 설정 파일(settings.json)에 적어요. JSON을 직접 쓰기 어렵다면 "Claude가 내 입력을 기다릴 때 맥 알림 띄우는 훅 만들어줘"처럼 부탁해도 돼요. 만든 뒤 /hooks로 목록을 확인해요.

    🧪 예시

    상황: 긴 브랜드 리서치를 돌려 두고 딴 창에서 피치덱을 만들다 보면, Claude가 확인을 기다리는 걸 자꾸 놓쳐요.

    Claude가 내 입력을 기다릴 때 맥 알림이 뜨는 훅을 만들어서 ~/.claude/settings.json에 넣어줘

    결과: 아래 "알림 훅 예시"와 같은 설정이 들어가요. 그다음부턴 Claude가 허락이나 답을 기다릴 때마다 화면 구석에 알림이 떠요. 훅이라서 빠지는 날이 없어요.

    더 알아보기: 알림 훅 예시 (macOS) 
    {
  "hooks": {
    "Notification": [
      {
        "matcher": "",
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude Code needs your attention\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}

    공식 문서의 첫 훅 예시예요. ~/.claude/settings.json에 넣으면 Claude가 기다릴 때마다 맥 알림이 떠요.

    알림이 안 뜨면 먼저 터미널에서 osascript -e 'display notification "test"'를 한 번 실행하세요. 그다음 시스템 설정 → 알림에서 '스크립트 편집기(Script Editor)'를 찾아 알림 허용을 켜요.

    서브에이전트(Subagent): 따로 일하고 요약만 주는 조수

    서브에이전트는 메인 대화와 분리된 컨텍스트에서 일하는 조수예요. 자료를 잔뜩 뒤지는 일을 맡기면, 조수가 그 자료를 다 읽고 요약만 돌려줘요. 내 대화창은 깨끗하게 유지되죠.

    • Claude는 코드나 폴더를 훑어볼 때 기본 제공되는 Explore 같은 서브에이전트에 알아서 맡기기도 해요.
    • 나만의 서브에이전트는 마크다운 파일 하나예요. 프로젝트용은 .claude/agents/, 내 모든 프로젝트용은 ~/.claude/agents/에 둬요.
    • 만들기는 "리서치 전담 서브에이전트 만들어줘"처럼 Claude에게 부탁하는 게 제일 쉬워요. 최신 버전에서 /agents는 이 방법을 안내하는 메시지만 보여줘요.
    🧪 예시

    상황: 대구 관광 콘텐츠 기획에 필요한 조사 세 가지를 한꺼번에 맡기고 싶어요.

    서브에이전트 3개로 나눠서 동성로 맛집, 근대골목 역사, 경쟁 관광 콘텐츠를 각각 조사하고 요약만 가져와줘

    결과(예시): 조수 셋이 각자 웹을 찾아 읽어요. 메인 대화에는 원문 대신 주제마다 몇 줄짜리 요약만 남아서, 이어서 "그럼 코스 짜줘"라고 해도 대화가 가볍게 유지돼요.

    📌 서브에이전트도 각자 요청을 보내서 사용량은 똑같이 차감돼요. 조수를 많이 부르면 그만큼 빨리 닳아요.

    프롬프트 기초: AI에게 일 잘 맡기는 법

    3줄 요약
    • 프롬프트(prompt)는 AI에게 보내는 요청서예요. AI는 내 머릿속을 모르니까 적어준 만큼만 알아요.
    • 좋은 요청은 역할 · 맥락 · 작업 · 형식 · 제약 다섯 칸을 채워요. 예시까지 붙이면 더 좋아요.
    • 처음부터 완벽할 필요 없어요. 짧게 시작해서 대화로 다듬고, 막히면 AI에게 먼저 질문하게 하세요.

    프롬프트가 뭐예요?

    Claude 채팅창이나 Claude Code 입력창에 치는 글이 전부 프롬프트예요. 질문이든 지시든 파일 정리 부탁이든 다 포함돼요.

    AI는 똑똑하지만 우리 수업, 우리 팀, 우리 브랜드 사정은 하나도 몰라요. 그래서 같은 AI라도 요청을 어떻게 쓰느냐에 따라 결과가 크게 달라져요.

    비유 오늘 처음 출근한 똑똑한 인턴에게 일을 맡긴다고 생각해 보세요. "보고서 하나 써줘"라고만 하면 인턴은 뭘 써야 할지 몰라 대충 무난한 걸 가져와요. 누가 읽을 건지, 왜 필요한지, 어떤 모양으로 언제까지인지 알려줘야 원하는 결과가 나와요. AI도 똑같아요.
    🧪 예시

    상황: 팀 프로젝트로 대구 관광 숏폼을 만드는데 제목 아이디어가 필요해요.

    숏폼 제목 추천해줘.

    결과: "꼭 가봐야 할 여행지 TOP 5"처럼 어디에나 붙는 제목이 나와요. 여기에 "대구 근대골목, 20대 커플 대상, 30초 릴스" 한 줄만 붙여도 우리 콘텐츠에 맞는 제목으로 바뀌어요.

    좋은 요청의 5칸 (+ 예시)

    잘 쓴 프롬프트를 뜯어보면 대부분 아래 다섯 칸이 채워져 있어요. 매번 다 쓸 필요는 없지만, 결과가 마음에 안 들 때 빈칸부터 확인해 보세요.

    칸스스로에게 묻기예시 문장
    역할어떤 전문가처럼 답하면 좋을까?"너는 뷰티 브랜드 MD야."
    맥락왜 필요하고, 누가 볼까?"다음 주 팀 회의에서 신상품 아이디어로 발표할 거야."
    작업정확히 뭘 해달라는 건가?"20대 여성 대상 비건 선크림 기획안 3개를 제안해줘."
    형식결과물이 어떤 모양이면 바로 쓸 수 있나?"표로. 열은 상품명, 타깃, 핵심 문구, 예상 가격대."
    제약지켜야 할 조건, 피할 것은?"한 줄 문구는 15자 이내. 과장 광고 표현은 빼줘."
    예시 (선택)내가 원하는 느낌을 보여줄 수 있나?"문구 톤은 '바르는 순간 산뜻하게' 같은 느낌으로."
    💡 다섯 칸 중 제일 자주 빠지는 건 맥락이에요. "누가, 왜 쓰는지" 한 줄만 붙여도 결과가 확 좋아져요.
    🧪 예시

    상황: 올리브영 신상품 기획 과제예요. 위 표의 문장을 순서대로 이어 붙이면 이런 프롬프트가 돼요.

    너는 뷰티 브랜드 MD야.
다음 주 팀 회의에서 신상품 아이디어로 발표할 거야.

    결과: 4열짜리 표에 기획안 3개가 채워져 나와요. 모양이 정해져 있어서 회의 슬라이드에 거의 그대로 붙일 수 있어요.

    😕 이렇게 말고
    별로야. 다시.
    ✅ 이렇게
    2번 캡션 톤이 딱 좋아. 1번, 3번도 그 톤으로 바꿔줘.
해시태그는 너무 흔한 #선크림 말고 상황형으로 (#등굣길 #출근메이크업 같은).
    💡 대화가 너무 길어지고 방향이 꼬였다면, 지금까지 정한 내용을 요약해 달라고 한 뒤 새 대화에서 그 요약으로 다시 시작하는 게 더 빨라요. Claude Code에서는 /compact로 대화를 요약해 줄이거나 /clear로 새로 시작할 수 있어요 (명령어 장 참고).

    AI에게 먼저 질문하게 하기

    내가 뭘 원하는지 나도 정확히 모를 때가 있어요. 그럴 땐 AI에게 바로 만들라고 하지 말고 질문부터 하라고 시켜 보세요.

    ✅ 이렇게
    대구 여행 숏폼 콘텐츠 기획을 도와줘.
바로 만들지 말고, 좋은 기획에 필요한 정보를 나한테 먼저 물어봐.
질문은 한 번에 하나씩, 네가 추천하는 답도 같이 보여줘.

    AI가 타깃, 플랫폼, 분량, 톤을 하나씩 물어오면 답하는 동안 내 생각도 정리돼요. 이 방식은 다음 장의 인터뷰형 프롬프트에서 더 자세히 다뤄요.

    복사해서 쓰는 템플릿

    아래 틀을 메모장에 저장해 두고 빈칸만 채워서 쓰세요. 필요 없는 줄은 지워도 돼요.

    [역할] 너는 ______ 야.
[맥락] ______ 를 위해 필요해. 결과는 ______ 가 보게 돼.
[작업] ______ 를 해줘.
[형식] ______ (표 / 목록 / 문단 / 파일로 저장) 로 정리해줘.
[제약] ______ 는 지키고, ______ 는 하지 마. 분량은 ______.
[예시] 이런 느낌이면 좋겠어: ______
[확인] 부족한 정보가 있으면 시작하기 전에 먼저 물어봐.
    🧪 예시

    상황: 팀 프로젝트 피치덱의 "문제 정의" 슬라이드 문구가 필요해요. 템플릿 빈칸을 채우면 이렇게 돼요.

    [역할] 너는 스타트업 피치덱 코치야.
[맥락] 대구 로컬 굿즈 스토어 피치덱이야. 결과는 데모데이 심사위원이 보게 돼.
[작업] "문제 정의" 슬라이드 문구를 써줘.
[형식] 제목 1줄 + 불릿 3개로 정리해줘.
[제약] 불릿은 20자 이내. 확인 안 된 숫자는 쓰지 마.

    결과: 슬라이드에 바로 옮길 제목 한 줄과 짧은 불릿 3개가 나와요. 이번엔 필요 없어서 [예시]와 [확인] 줄은 지웠어요.

    더 깊이 알고 싶다면 Anthropic 공식 가이드를 참고하세요. Anthropic 프롬프트 엔지니어링 가이드 ↗

    프롬프트 엔지니어링 기초: 자주 쓰는 기법 10가지

    3줄 요약
    • 프롬프트 엔지니어링은 거창한 기술이 아니라 "AI가 잘 알아듣게 쓰는 요령" 모음이에요.
    • 예시 보여주기, 단계별로 생각시키기, 자료와 지시를 태그로 나누기, 출력 모양 정하기가 기본기예요.
    • 큰 일은 여러 프롬프트로 나눠 잇고, AI가 스스로 검토하게 하고, 사실은 출처로 확인하세요.
    📌 이 장의 🧪 예시에 나오는 AI 답은 이해를 돕기 위한 예시 답변이에요. 실제 답은 매번 달라요.

    제로샷 · 원샷 · 퓨샷

    샷(shot)은 프롬프트에 넣는 예시 개수예요. 예시가 없으면 제로샷, 하나면 원샷, 여러 개면 퓨샷(few-shot, 멀티샷)이라고 불러요.

    제로샷

    간단하고 흔한 일에 써요.
    대구 서문시장 소개 문장 한 줄 써줘.

    원샷

    원하는 모양을 하나 보여줘요.
    예: "동성로 | 밤 9시에도 반짝이는 대구의 심장" 이 형식으로 김광석길도 써줘.

    퓨샷

    브랜드 톤처럼 미묘한 스타일을 맞출 때 써요. 예시는 2~5개를 서로 조금씩 다르게 넣어요. 아래 박스를 보세요.

    ✅ 퓨샷 예시
    우리 브랜드 상품 한 줄 소개는 이런 톤이야.
- 사과 립밤: "대구 사과처럼, 입술에 가을 한 입"
- 녹차 클렌저: "세안이 끝나면 숲에서 돌아온 기분"
- 쌀 토너: "밥심 말고 피부심"

같은 톤으로 "보리 수분크림" 소개 3개 써줘.
    🧪 예시

    상황: 같은 "보리 수분크림 소개 한 줄"을 예시 없이 한 번, 위처럼 예시 3개를 넣고 한 번 요청했어요. 예시 답변:

    제로샷: "보리 추출물로 촉촉하게 채워주는 수분크림"
퓨샷:   "보리차처럼 순하게, 피부에 한 모금"

    결과: 제로샷은 어느 브랜드에나 붙는 설명이 나오고, 퓨샷은 우리 브랜드처럼 비유를 넣은 짧은 톤을 따라 해요.

    생각의 사슬 (Chain of Thought)

    복잡한 문제는 바로 답하게 하면 실수가 잦아요. "단계별로 생각해줘"처럼 답 전에 생각 과정을 거치게 하면 정확도가 올라가요. 이걸 생각의 사슬(Chain of Thought, CoT)이라고 해요.

    ✅ 이렇게
    20대 타깃 뷰티 팝업스토어를 대구 동성로, 수성못, 대구역 중 어디에 열지 정하고 싶어.
바로 답하지 말고 단계별로 생각해줘.
1) 판단 기준 정하기 2) 후보지별로 기준 점수 매기기 3) 결론과 이유
    🧪 예시

    상황: 위 팝업스토어 질문을 "단계별로" 없이 보냈을 때와 넣었을 때 답이 달라져요. 예시 답변:

    바로 답: "동성로가 좋아요. 사람이 많거든요."
단계별:  1) 기준: 20대 방문, 임대료, 주말 접근성
         2) 기준마다 동성로 · 수성못 · 대구역 점수 비교
         3) 결론: 동성로. 임대료가 부담이면 수성못도 검토

    결과: 단계별 답은 근거가 보여서, 팀원이 "임대료 기준은 빼자"처럼 중간 단계를 짚어 고칠 수 있어요.

    📌 요즘 Claude 모델(Opus 5.5, Sonnet 5.5 등)은 답하기 전에 속으로 먼저 생각해요(확장 사고). 그래도 "단계별로"라고 쓰면 생각 과정이 답에 드러나서 어디가 틀렸는지 짚기 쉬워져요. 생각 깊이는 Claude Code에서 /effort로 바꿀 수 있어요. 예: /effort high (모델마다 고를 수 있는 단계가 달라요. 자세한 건 명령어 장).

    역할 부여 (Role Prompting)

    "너는 ○○야"라고 역할을 주면 AI가 그 분야의 관점과 말투로 답해요. 같은 기획안이라도 누구 눈으로 보느냐에 따라 피드백이 달라져요.

    ✅ 이렇게
    너는 10년 차 올리브영 MD야.
아래 신상품 기획안을 입점 심사하듯 읽고, 통과 가능성과 보완할 점 3가지를 말해줘.
    🧪 예시

    상황: 팀 과제로 쓴 "쌀 토너" 기획안을 역할 없이 한 번, MD 역할을 주고 한 번 봐달라고 했어요. 예시 답변:

    역할 없이: "전체적으로 잘 썼어요! 타깃을 조금 더 구체화하면 좋겠어요."
MD 역할:   "비슷한 토너와 뭐가 다른지 한 줄로 안 보여요. 심사에선 그게
           제일 먼저 걸려요. 가격대와 용량 근거도 보강하세요."

    결과: 역할을 주면 칭찬 위주의 두루뭉술한 답 대신, 그 일을 하는 사람이 실제로 짚을 만한 지점이 나와요.

    💡 매번 같은 역할과 규칙을 쓴다면 Claude Code의 CLAUDE.md에 적어두세요. 세션마다 자동으로 읽혀요. 자세한 건 Claude Code 구성요소 장에 있어요.

    구조화: 마크다운 · XML 태그

    자료와 지시가 한 덩어리로 섞이면 AI가 어디까지가 자료인지 헷갈려요. 마크다운 제목(##)이나 <자료>…</자료> 같은 태그로 칸을 나눠 주세요.

    비유 서류를 책상에 흩어놓고 "이거 정리해줘"라고 하는 것과, "계약서" "영수증" 라벨을 붙인 서류철을 건네는 것의 차이예요. 태그 이름은 한글이든 영어든 상관없고, 열고 닫는 이름만 맞으면 돼요.
    <자료>
(여기에 고객 리뷰 30개 붙여넣기)
</자료>

<지시>
위 자료에서 불만을 주제별로 묶고, 가장 많이 나온 3개를 골라줘.
</지시>

<형식>
주제 | 언급 수 | 대표 리뷰 한 줄
</형식>

    마크다운으로는 ## 자료, ## 지시, ## 형식처럼 제목 줄로 칸을 나눠도 돼요.

    🧪 예시

    상황: 대구 로컬 굿즈 스토어의 고객 리뷰 30개를 위 틀의 <자료> 칸에 붙여넣고 보냈어요. 예시 답변:

    주제 | 언급 수 | 대표 리뷰 한 줄
배송 지연 | 9 | "주문하고 일주일 넘게 걸렸어요"
포장 | 6 | "선물용인데 박스가 찌그러져 왔어요"
가격 | 4 | "굿즈치고 좀 비싸요"

    결과: 태그 없이 섞어 보내면 리뷰 전체를 길게 요약해 올 때가 있어요. 칸을 나누면 <형식>에 적은 모양 그대로 나와요. AI가 센 '언급 수'는 틀릴 수 있으니 발표에 쓸 숫자는 직접 세어 확인하세요.

    출력 형식 정하기: 표 · JSON · 체크리스트

    결과를 어디에 쓸지 먼저 생각하고 그 모양을 지정하세요. 회의 자료면 표, 다른 도구(n8n, 웹사이트)에 넣을 거면 JSON(프로그램끼리 데이터를 주고받을 때 쓰는 '이름: 값' 모양의 글 형식), 할 일이면 체크리스트가 편해요.

    표

    열은 장소 | 추천 시간대 | 한 줄 팁 으로 표 만들어줘.

    JSON

    {"name": "", "category": "", "price": 0} 형식의 JSON 배열로만 답해줘. 설명 문장은 빼고.

    체크리스트

    프롬프트 체이닝 (Prompt Chaining)

    큰 일을 한 프롬프트에 몰아넣으면 품질이 떨어져요. 단계를 나눠 앞 단계 결과를 다음 프롬프트에 넘기는 방식을 프롬프트 체이닝이라고 해요.

    인터뷰형 프롬프트 (AI가 질문하기)

    아이디어가 흐릿할 때는 AI가 나를 인터뷰하게 하세요. 한 번에 하나씩 묻고 추천 답을 같이 주게 하면, 답하기 쉬우면서 빠진 부분이 채워져요. 수업의 "인터뷰형 spec.md 작성"이 바로 이 방식이에요.

    할루시네이션 확인하기

    할루시네이션(hallucination)은 AI가 없는 사실을 그럴듯하게 지어내는 현상이에요. 숫자, 날짜, 인물, 출처 링크에서 특히 자주 생겨요.

    ✅ 이렇게
    각 주장마다 출처 링크와 근거가 된 문장을 같이 적어줘.
확실하지 않은 내용은 "확인 필요"라고 표시하고, 모르면 모른다고 말해도 돼.
    🧪 예시

    상황: 피치덱에 넣을 "대구 연간 관광객 수"를 위 프롬프트와 함께 물었어요. 예시 답변:

    - 지역별 관광 통계는 한국관광 데이터랩에서 볼 수 있어요. (링크)

    결과: "확인 필요"가 붙은 칸은 링크를 직접 열어 숫자를 찾아 채워요. AI가 숫자를 줬더라도 원문과 맞는지 보고 나서 슬라이드에 넣어요.

    ⚠️ 발표 자료나 상세페이지에 들어갈 숫자(매출, 방문객 수, 성분 함량)는 반드시 원문을 열어 확인하세요. 중요한 내용은 다른 AI나 검색으로 한 번 더 교차검증하면 안전해요.

    챗봇 vs 에이전트: 답하는 AI와 일하는 AI

    Claude.ai 채팅창에 "대구 로컬 브랜드 조사해 줘"라고 하면 답변 글이 돌아와요. 그걸 복사해서 파일로 저장하고 정리하는 건 여러분 몫이에요.

    Claude Code에 같은 말을 하면 조금 달라요. 폴더를 살펴보고, 검색하고, brands.md 파일을 직접 만들고, 빠진 게 없는지 다시 읽어 봐요. 결과물이 파일로 남아요.

    비유 챗봇은 전화로 레시피를 알려 주는 친구, 에이전트는 우리 집 부엌에 와서 직접 요리하고 간까지 보는 친구예요. 대신 부엌에 들일 땐 어디까지 만져도 되는지 정해 줘야 해요(권한).
    🧪 예시

    1. 컨텍스트 모으기: 파일을 읽고, 검색하고, 무엇을 바꿔야 할지 파악해요.
    2. 행동하기: 파일을 고치고, 명령어를 실행해요.
    3. 결과 확인하기: 잘 됐는지 확인하고, 아니면 1번으로 돌아가 방법을 바꿔요.

    하네스(harness): 엔진과 차체

    Claude 모델 자체는 글을 읽고 쓰는 능력만 있어요. 파일을 열고, 명령을 실행하고, 권한을 묻고, 대화를 기억하게 해 주는 건 모델을 감싸고 있는 프로그램이에요. 이 바깥 틀을 하네스(harness)라고 불러요. Claude Code가 바로 하네스예요.

    비유 모델은 엔진, 하네스는 차체·핸들·브레이크예요. 엔진이 아무리 좋아도 핸들과 브레이크가 없으면 도로에 나갈 수 없어요. 같은 엔진이라도 어떤 차에 얹느냐에 따라 운전감이 달라져요.

    하네스 엔지니어링은 이 차를 내 일에 맞게 튜닝하는 걸 말해요. 그림의 '내가 하는 튜닝' 상자에 있는 CLAUDE.md, 스킬, 훅, 서브에이전트처럼 수업에서 배우는 것들이 전부 여기에 들어가요.

    🧪 예시

    상황: 피치덱 작업을 할 때마다 "답은 한국어로, 파일은 output 폴더에"를 매번 다시 말하고 있어요.

    # CLAUDE.md에 한 번만 적어 두기
- 답은 항상 한국어로
- 만든 파일은 output 폴더에 저장

    결과: 적어 두기 전엔 매번 같은 말을 붙여야 했어요. 적어 둔 뒤엔 "피치덱 표지 문구 써 줘"만 해도 한국어로 써서 output 폴더에 저장해요. 엔진(모델)은 그대로고 차체(하네스)만 튜닝한 거예요.

    워크플로우 vs 에이전트, 그리고 5가지 패턴

    Anthropic은 AI로 일을 엮는 방식을 둘로 나눠요. 워크플로우(workflow)는 사람이 미리 정해 둔 길을 따라가요. 에이전트(agent)는 다음에 뭘 할지 모델이 그때그때 정해요.

    비유 워크플로우는 정해진 노선을 도는 시내버스, 에이전트는 목적지만 말하면 길을 알아서 고르는 택시예요. 버스는 예측 가능하고, 택시는 유연해요.

    정해진 순서로 매번 똑같이 돌아가야 하면 워크플로우가 맞아요(n8n 자동화가 대표적이에요). 무엇을 해야 할지 상황마다 다르면 에이전트가 맞아요. 아래 다섯 패턴은 Anthropic 글 Building effective agents ↗에서 소개한 것들이에요.

    패턴한 줄 설명일상 예
    ① 프롬프트 체이닝(chaining)한 단계의 결과를 다음 단계에 넘겨요. 중간에 검사 관문을 둘 수 있어요.브랜드 조사 → 핵심 메시지 → 인스타 문구
    ② 라우팅(routing)입력 종류를 먼저 나눈 다음, 각각에 맞는 담당에게 보내요.고객 문의를 상품·배송·불만 창구로 나누기
    ③ 병렬화(parallelization)서로 상관없는 일을 동시에 돌리고 결과를 합쳐요.동성로·서문시장·앞산을 동시에 조사
    ④ 오케스트레이터-워커(orchestrator-workers)반장 역할 AI가 일을 쪼개서 나눠 주고 결과를 모아요. 몇 개로 나눌지도 반장이 정해요.신상품 기획을 경쟁사·타깃 고객·가격대로 나눠 맡기기
    ⑤ 평가자-최적화(evaluator-optimizer)한쪽이 만들고 다른 쪽이 기준에 맞춰 평가해요. 통과할 때까지 반복해요.글쓴이와 편집자가 상세페이지 문구 주고받기

    자주 쓰는 ⑤ 평가자-최적화를 그림으로 볼게요. ① 체이닝은 바로 아래 예시로, 나머지는 "패턴 그림 더 보기"에서 볼 수 있어요.

    패턴 그림 더 보기
    💡 처음부터 복잡하게 짤 필요 없어요. Anthropic도 "가장 단순한 방법부터 시작하고, 필요할 때만 복잡하게"를 권해요.

    서브에이전트와 병렬 작업

    서브에이전트(subagent)는 메인 Claude가 부르는 보조 일꾼이에요. 핵심은 각자 자기 컨텍스트 창을 따로 쓴다는 점이에요. 서브에이전트가 웹페이지 열 개를 읽어도, 메인 대화에는 요약만 돌아와요.

    비유 팀장이 인턴 세 명에게 조사를 맡기면, 인턴들은 각자 책상에서 자료를 잔뜩 펼쳐요. 팀장 책상에는 한 장짜리 보고서만 올라와요. 팀장 책상(메인 컨텍스트)이 깨끗하게 유지돼요.

    Ralph 루프: 될 때까지 다시 돌리기

    Ralph 루프(Ralph Wiggum 기법)는 개발자 Geoffrey Huntley가 2025년에 알린 방법이에요(만화 심슨 가족의 엉뚱하지만 끈질긴 캐릭터 이름에서 따왔어요). 같은 작업 지시를 에이전트에게 몇 번이고 다시 줘요. 매 라운드마다 에이전트는 현재 파일과 결과를 새로 읽고, 완료 기준을 통과할 때까지 이어서 일해요.

    이 방법에서 가장 중요한 건 완료 기준이에요. "좋아질 때까지"는 끝이 없어요. "체크리스트 10개 모두 체크", "모든 상품에 가격과 출처 링크가 있음"처럼 눈으로 확인할 수 있어야 루프가 멈춰요.

    상세페이지 문구 좋아질 때까지 계속 고쳐 줘.

1) 200자 이내  2) 성분 이름 2개 이상  3) 과장 표현(최고, 1위) 없음

    Git & GitHub 기초

    3줄 요약
    • Git은 내 컴퓨터에 남기는 세이브 포인트, GitHub는 그 세이브 파일을 올려 두는 클라우드예요.
    • 명령어를 외울 필요는 없어요. Claude Code에 "지금까지 작업 커밋해줘"처럼 말로 시키면 돼요.
    • GitHub에 올리면 Vercel이 알아서 웹사이트로 배포해 줘요. 단, .env와 API 키는 절대 올리면 안 돼요.

    왜 Git을 써야 할까요?

    Claude Code는 파일을 직접 고쳐요. 일이 잘 풀릴 땐 좋지만, 가끔 멀쩡하던 페이지를 엉뚱하게 바꿔 놓기도 해요. 그럴 때 "어제 잘 되던 버전"으로 돌아갈 수 있어야 마음 편히 실험할 수 있어요.

    비유 게임 보스전 앞에서 세이브하는 것과 같아요. 지면 세이브 포인트에서 다시 시작하면 되니까 과감하게 도전할 수 있죠. Google Docs의 "버전 기록"을 떠올려도 좋아요. 차이는 Git은 내가 원하는 순간에, 이름을 붙여서 저장한다는 점이에요.

    그래서 Git을 쓰면 이런 게 가능해져요.

    • "올리브영 기획안 v2" 시점으로 언제든 되돌리기
    • 무엇이 언제 왜 바뀌었는지 기록 보기
    • 원본은 그대로 두고 새 아이디어를 따로 시험해 보기
    📌 Claude Code에도 체크포인트가 있어요. 터미널에서는 입력창이 비어 있을 때 Esc Esc를 누르거나 /rewind를 치면 이전 시점으로 돌아갈 수 있어요. 하지만 이건 세션 안에서 쓰는 "실행 취소"에 가까워요. 며칠, 몇 주 단위로 남기는 기록은 Git이 맡아요. 데스크톱 앱에서는 Esc가 응답을 멈추는 키예요.
    🧪 예시

    상황: 올리브영 신상품 기획안 페이지를 다듬다가 Claude가 어제 잘 되던 가격표까지 바꿔 버렸어요.

    어제 커밋이랑 지금 뭐가 달라졌는지 보여줘. 가격표만 어제 커밋 상태로 돌려줘. 되돌리기 전에 방법부터 설명해줘.

    결과: 바뀐 줄 목록과 되돌리는 방법을 먼저 보여 주고, 확인하면 가격표만 어제 버전으로 돌아와요. 나머지 오늘 작업은 그대로 남아요.

    Git과 GitHub는 다른 거예요

    이름이 비슷해서 많이 헷갈려요. Git은 내 컴퓨터에 설치하는 기록 프로그램이고, GitHub는 그 기록을 인터넷에 올려 두는 웹사이트예요.

    비유 Git이 휴대폰 사진첩이라면 GitHub는 구글 포토 같은 클라우드 백업이에요. 사진첩만 있어도 사진은 찍히지만, 폰을 잃어버리면 끝이죠. 클라우드에 올려 두면 다른 기기에서도 보고 친구와 공유도 할 수 있어요.
    🧪 예시

    상황: 대구 로컬 브랜드 랜딩페이지 파일을 고치고 저장(Ctrl+S)만 해 둔 상태예요. 이 저장소는 이미 GitHub에 연결돼 있어요.

    지금까지 작업 커밋해줘.
(GitHub 저장소 페이지를 새로고침해 봐요)
이제 push해줘.
(다시 새로고침)

    결과: 커밋만 했을 땐 GitHub 화면에 아무 변화가 없어요. push한 뒤에야 방금 커밋 메모가 GitHub에 보여요. 커밋은 내 컴퓨터, push는 인터넷이라는 게 바로 이 차이예요.

    꼭 알아야 할 단어 9개

    📦 저장소 (repository, repo)

    Git이 기록을 관리하는 프로젝트 폴더 하나예요. "대구 로컬 브랜드 랜딩페이지" 폴더 하나가 repo 하나라고 보면 돼요.

    💾 커밋 (commit)

    세이브 포인트 하나예요. "메인 문구 수정"처럼 짧은 메모를 붙여서 저장해요.

    🌿 브랜치 (branch)

    원본을 건드리지 않고 갈라져 나온 작업 줄기예요. 기본 줄기는 보통 main이에요.

    🔀 머지 (merge)

    브랜치에서 만든 결과를 main에 합치는 거예요.

    ⬆️ 푸시 (push)

    내 컴퓨터의 커밋을 GitHub로 올리는 거예요.

    ⬇️ 풀 (pull)

    GitHub에 있는 최신 커밋을 내 컴퓨터로 받아오는 거예요.

    🧬 클론 (clone)

    GitHub에 있는 저장소를 통째로 내 컴퓨터에 복사해 오는 거예요. 처음 한 번만 해요.

    🙋 PR (Pull Request)

    "이 브랜치를 main에 합쳐도 될까요?" 하고 GitHub에서 올리는 검토 요청이에요. 팀 프로젝트에서 많이 써요.

    🙈 .gitignore

    "이 파일은 기록하지 마"라는 목록 파일이에요. .env, node_modules 같은 걸 적어 둬요.

    🧪 예시

    상황: 피치덱 팀 프로젝트에 합류했어요. 팀장이 GitHub 저장소 주소를 보내 줬어요.

    이 GitHub 저장소 clone해줘: (팀장이 준 주소 붙여넣기)
최근 커밋 5개가 각각 뭘 바꿨는지 쉽게 설명해줘.

    결과: 내 컴퓨터에 저장소(repo) 폴더가 생기고, "표지 디자인 수정", "시장 규모 슬라이드 추가" 같은 커밋 기록을 한글로 풀어서 보여 줘요.

    브랜치는 이렇게 생겼어요

    예를 들어 관광 콘텐츠 사이트에 "맛집 지도" 기능을 새로 붙인다고 해 볼게요. 잘 돌아가는 main은 그대로 두고, 옆 줄기에서 실험한 다음 괜찮으면 합쳐요.

    💡 혼자 하는 작은 과제라면 main 하나에 자주 커밋하는 것만으로 충분해요. 브랜치는 "이거 망칠 수도 있는데?" 싶은 큰 변경 때 쓰면 돼요.
    🧪 예시

    상황: feature 브랜치에서 맛집 지도를 붙여 봤는데, 결과가 마음에 드는 경우와 안 드는 경우를 둘 다 볼게요.

    마음에 들 때: feature 브랜치 작업을 main에 합쳐줘.
마음에 안 들 때: 이 브랜치는 그만할래. main으로 돌아가줘.

    결과: 합치면 main에 지도 기능이 들어가요. 그만두면 main은 지도를 붙이기 전 모습 그대로라서 잃는 게 없어요.

    .gitignore와 API 키: 제일 중요한 규칙

    ⚠️ API 키, 비밀번호가 들어 있는 .env 파일은 절대 커밋하지 마세요. 공개 저장소에 한 번 올라가면 몇 분 만에 자동 수집기가 긁어 가고, 내 카드로 요금이 청구될 수 있어요. 나중에 파일을 지워도 Git 기록에는 남아 있어요.

    그래서 저장소를 만들 때 .gitignore부터 챙겨요. 내용은 이 정도로 시작하면 돼요.

    .env
.env.local
node_modules/
.DS_Store

    Claude Code에 이렇게 부탁하면 확인까지 같이 해 줘요.

    ✅ 이렇게
    커밋하기 전에 .gitignore 확인해줘. .env나 API 키가 들어간 파일이 올라가지 않게 막아주고, 이미 추적 중인 비밀 파일이 있으면 알려줘.
    🧪 예시

    상황: 대구 관광 콘텐츠 페이지에 날씨 API 키를 .env에 넣어 뒀어요.

    git status 결과 보여주고, .env가 커밋 대상에 들어 있는지 알려줘.

    결과: .gitignore에 .env가 적혀 있으면 바뀐 파일 목록에 .env가 아예 안 나와요. 목록에 보인다면 커밋하기 전에 막아야 한다는 신호예요.

    📌 실수로 키를 올렸다면, 파일을 지우는 것보다 먼저 해당 서비스에서 키를 폐기하고 새로 발급하세요.

    GitHub에서 Vercel까지: 배포 흐름

    수업 후반에 만든 페이지를 Vercel로 배포해요. GitHub 저장소를 Vercel에 한 번 연결해 두면, 그 다음부터는 push만 해도 사이트가 자동으로 새로 만들어져요. 처음 연결은 이렇게 해요.

    1. vercel.com에서 Continue with GitHub로 가입해요.
    2. Add New → Project를 눌러요.
    3. 올릴 저장소 옆 Import를 누르고 Deploy를 눌러요.
    4. 1~2분 뒤 나오는 …vercel.app 주소가 내 사이트예요.
    비유 GitHub는 원고를 넣는 우편함, Vercel은 우편함에 새 원고가 들어오는 순간 알림을 받고 바로 인쇄해 서점에 거는 출판사예요. 나는 원고만 넣으면 돼요.
    📌 .env는 GitHub에 안 올라가니까 Vercel도 키를 몰라요. 내 컴퓨터에선 잘 되던 사이트가 배포 후 깨진다면 대개 이 이유예요. Vercel 프로젝트의 Settings → Environment Variables에 같은 이름과 값을 직접 넣어 줘야 해요.
    🧪 예시

    상황: Vercel에 연결해 둔 대구 로컬 카페 랜딩페이지의 메인 문구를 바꾸고 싶어요.

    메인 문구를 "대구의 아침, 한 잔의 커피"로 바꾸고 커밋하고 push해줘.

    결과: push가 끝나고 잠시 뒤 Vercel 공개 URL을 새로고침하면 바뀐 문구가 보여요. Vercel 사이트에 따로 들어가서 버튼을 누를 필요는 없어요.

    Claude Code로 말로 하는 Git

    Git 명령어를 몰라도 괜찮아요. Claude Code가 터미널 명령을 대신 실행해 주니까 하고 싶은 일을 말로 설명하면 돼요. 다만 무엇을 했는지 결과 설명은 꼭 읽어 보세요.

    하고 싶은 일이렇게 말해 보세요
    처음 Git 시작"이 폴더를 Git 저장소로 만들고 .gitignore도 만들어줘"
    세이브하기"지금까지 작업 커밋해줘. 메시지는 변경 내용 요약으로"
    뭐가 바뀌었나 보기"마지막 커밋 이후 바뀐 내용 쉽게 설명해줘"
    GitHub에 처음 올리기"GitHub에 새 비공개 저장소 만들고 올려줘"
    이후 올리기"커밋하고 push해줘"
    실험용 줄기"맛집 지도 작업용 브랜치 만들어서 거기서 작업해줘"
    되돌리기"어제 커밋 상태로 되돌리고 싶어. 어떤 방법이 안전한지 먼저 설명해줘"
    ⚠️ "GitHub에 새 저장소 만들어줘"가 되려면 준비가 필요해요. 먼저 github.com에서 무료 계정을 만들어 두세요. 그다음 컴퓨터에 Git과 GitHub CLI(gh)를 설치하고, 터미널에서 gh auth login으로 GitHub 로그인을 한 번 해 둬야 해요. 설치나 로그인이 안 돼 있으면 Claude에게 "gh 설치하고 로그인하는 방법 단계별로 알려줘"라고 물어보세요.
    💡 되돌리기, 강제 push처럼 기록을 지울 수 있는 작업은 바로 시키지 말고 "먼저 설명해줘"를 붙이세요. 확인하고 나서 진행해도 늦지 않아요.
    🧪 예시

    상황: 올리브영 마케팅 카드뉴스 HTML을 세 장 만들고 세이브하려고 해요.

    지금까지 작업 커밋해줘. 메시지는 변경 내용 요약으로.

    결과: Claude가 git add, git commit 같은 명령을 실행하고 "카드뉴스 1~3장 추가" 같은 메시지로 저장했다고 알려 줘요. 권한 모드에 따라 실행 전에 허락을 물으면 명령을 읽어 보고 허용하면 돼요.

    터미널이 무섭다면: GitHub Desktop

    버튼으로 Git을 쓰고 싶다면 GitHub Desktop ↗도 좋아요. 바뀐 파일 목록을 눈으로 보고, 커밋 메모를 적고, Push 버튼을 누르는 식이에요. Claude Code로 작업하고 GitHub Desktop으로 확인하는 조합도 초보에게 편해요.

    🧪 예시

    상황: Claude Code가 팀 피치덱 파일을 고쳤는데, 정확히 어디가 바뀌었는지 눈으로 보고 싶어요.

    아직 커밋하지 말고 그대로 둬. 내가 GitHub Desktop에서 먼저 확인할게.

    결과: GitHub Desktop의 Changes 탭에 바뀐 파일 목록이 뜨고, 지운 줄은 빨간색, 추가한 줄은 초록색으로 보여요. 확인한 뒤 거기서 바로 커밋해도 돼요.

    매일 작업 루틴 체크리스트

    1. 시작할 때 다른 컴퓨터나 팀원이 바꾼 게 있다면 "최신 내용 pull해줘"
    2. 작업 중 의미 있는 단위가 끝날 때마다 "지금까지 커밋해줘" (예: 헤더 완성, 상품 표 추가)
    3. 위험한 실험 전 커밋 먼저, 또는 브랜치 만들기
    4. 올리기 전 ".env나 키가 섞여 있지 않은지 확인해줘"
    5. 끝낼 때 "커밋하고 push해줘" 후 Vercel 공개 URL에서 결과 확인

    이 순서대로 저녁에 40분만 손봐도 세이브 포인트가 두세 개 생기고, GitHub와 Vercel 사이트가 오늘 작업으로 바뀌어 있어요. 내일 상품 표가 망가져도 헤더 완성 시점으로 돌아갈 수 있어요.

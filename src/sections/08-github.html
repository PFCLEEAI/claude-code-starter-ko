Git & GitHub 기초

3줄 요약
  • Git은 내 컴퓨터에 남기는 세이브 포인트, GitHub는 그 세이브 파일을 올려 두는 클라우드예요.
  • 명령어를 외울 필요는 없어요. Claude Code에 "지금까지 작업 커밋해줘"처럼 말로 시키면 돼요.
  • GitHub에 올리면 Vercel이 알아서 웹사이트로 배포해 줘요. 단, .env와 API 키는 절대 올리면 안 돼요.

왜 Git을 써야 할까요?

Claude Code는 파일을 직접 고쳐요. 일이 잘 풀릴 땐 좋지만, 가끔 멀쩡하던 페이지를 엉뚱하게 바꿔 놓기도 해요. 그럴 때 "어제 잘 되던 버전"으로 돌아갈 수 있어야 마음 편히 실험할 수 있어요.

비유 게임 보스전 앞에서 세이브하는 것과 같아요. 지면 세이브 포인트에서 다시 시작하면 되니까 과감하게 도전할 수 있죠. Google Docs의 "버전 기록"을 떠올려도 좋아요. 차이는 Git은 내가 원하는 순간에, 이름을 붙여서 저장한다는 점이에요.

그래서 Git을 쓰면 이런 게 가능해져요.

  • "올리브영 기획안 v2" 시점으로 언제든 되돌리기
  • 무엇이 언제 왜 바뀌었는지 기록 보기
  • 원본은 그대로 두고 새 아이디어를 따로 시험해 보기
📌 Claude Code에도 체크포인트가 있어요. 터미널에서는 입력창이 비어 있을 때 Esc Esc를 누르거나 /rewind를 치면 이전 시점으로 돌아갈 수 있어요. 하지만 이건 세션 안에서 쓰는 "실행 취소"에 가까워요. 며칠, 몇 주 단위로 남기는 기록은 Git이 맡아요. 데스크톱 앱에서는 Esc가 응답을 멈추는 키예요.
🧪 예시

상황: 올리브영 신상품 기획안 페이지를 다듬다가 Claude가 어제 잘 되던 가격표까지 바꿔 버렸어요.

어제 커밋이랑 지금 뭐가 달라졌는지 보여줘. 가격표만 어제 커밋 상태로 돌려줘. 되돌리기 전에 방법부터 설명해줘.

결과: 바뀐 줄 목록과 되돌리는 방법을 먼저 보여 주고, 확인하면 가격표만 어제 버전으로 돌아와요. 나머지 오늘 작업은 그대로 남아요.

Git과 GitHub는 다른 거예요

이름이 비슷해서 많이 헷갈려요. Git은 내 컴퓨터에 설치하는 기록 프로그램이고, GitHub는 그 기록을 인터넷에 올려 두는 웹사이트예요.

비유 Git이 휴대폰 사진첩이라면 GitHub는 구글 포토 같은 클라우드 백업이에요. 사진첩만 있어도 사진은 찍히지만, 폰을 잃어버리면 끝이죠. 클라우드에 올려 두면 다른 기기에서도 보고 친구와 공유도 할 수 있어요.
🧪 예시

상황: 대구 로컬 브랜드 랜딩페이지 파일을 고치고 저장(Ctrl+S)만 해 둔 상태예요. 이 저장소는 이미 GitHub에 연결돼 있어요.

지금까지 작업 커밋해줘.
(GitHub 저장소 페이지를 새로고침해 봐요)
이제 push해줘.
(다시 새로고침)

결과: 커밋만 했을 땐 GitHub 화면에 아무 변화가 없어요. push한 뒤에야 방금 커밋 메모가 GitHub에 보여요. 커밋은 내 컴퓨터, push는 인터넷이라는 게 바로 이 차이예요.

꼭 알아야 할 단어 9개

📦 저장소 (repository, repo)

Git이 기록을 관리하는 프로젝트 폴더 하나예요. "대구 로컬 브랜드 랜딩페이지" 폴더 하나가 repo 하나라고 보면 돼요.

💾 커밋 (commit)

세이브 포인트 하나예요. "메인 문구 수정"처럼 짧은 메모를 붙여서 저장해요.

🌿 브랜치 (branch)

원본을 건드리지 않고 갈라져 나온 작업 줄기예요. 기본 줄기는 보통 main이에요.

🔀 머지 (merge)

브랜치에서 만든 결과를 main에 합치는 거예요.

⬆️ 푸시 (push)

내 컴퓨터의 커밋을 GitHub로 올리는 거예요.

⬇️ 풀 (pull)

GitHub에 있는 최신 커밋을 내 컴퓨터로 받아오는 거예요.

🧬 클론 (clone)

GitHub에 있는 저장소를 통째로 내 컴퓨터에 복사해 오는 거예요. 처음 한 번만 해요.

🙋 PR (Pull Request)

"이 브랜치를 main에 합쳐도 될까요?" 하고 GitHub에서 올리는 검토 요청이에요. 팀 프로젝트에서 많이 써요.

🙈 .gitignore

"이 파일은 기록하지 마"라는 목록 파일이에요. .env, node_modules 같은 걸 적어 둬요.

🧪 예시

상황: 피치덱 팀 프로젝트에 합류했어요. 팀장이 GitHub 저장소 주소를 보내 줬어요.

이 GitHub 저장소 clone해줘: (팀장이 준 주소 붙여넣기)
최근 커밋 5개가 각각 뭘 바꿨는지 쉽게 설명해줘.

결과: 내 컴퓨터에 저장소(repo) 폴더가 생기고, "표지 디자인 수정", "시장 규모 슬라이드 추가" 같은 커밋 기록을 한글로 풀어서 보여 줘요.

브랜치는 이렇게 생겼어요

예를 들어 관광 콘텐츠 사이트에 "맛집 지도" 기능을 새로 붙인다고 해 볼게요. 잘 돌아가는 main은 그대로 두고, 옆 줄기에서 실험한 다음 괜찮으면 합쳐요.

💡 혼자 하는 작은 과제라면 main 하나에 자주 커밋하는 것만으로 충분해요. 브랜치는 "이거 망칠 수도 있는데?" 싶은 큰 변경 때 쓰면 돼요.
🧪 예시

상황: feature 브랜치에서 맛집 지도를 붙여 봤는데, 결과가 마음에 드는 경우와 안 드는 경우를 둘 다 볼게요.

마음에 들 때: feature 브랜치 작업을 main에 합쳐줘.
마음에 안 들 때: 이 브랜치는 그만할래. main으로 돌아가줘.

결과: 합치면 main에 지도 기능이 들어가요. 그만두면 main은 지도를 붙이기 전 모습 그대로라서 잃는 게 없어요.

.gitignore와 API 키: 제일 중요한 규칙

⚠️ API 키, 비밀번호가 들어 있는 .env 파일은 절대 커밋하지 마세요. 공개 저장소에 한 번 올라가면 몇 분 만에 자동 수집기가 긁어 가고, 내 카드로 요금이 청구될 수 있어요. 나중에 파일을 지워도 Git 기록에는 남아 있어요.

그래서 저장소를 만들 때 .gitignore부터 챙겨요. 내용은 이 정도로 시작하면 돼요.

.env
.env.local
node_modules/
.DS_Store

Claude Code에 이렇게 부탁하면 확인까지 같이 해 줘요.

✅ 이렇게
커밋하기 전에 .gitignore 확인해줘. .env나 API 키가 들어간 파일이 올라가지 않게 막아주고, 이미 추적 중인 비밀 파일이 있으면 알려줘.
🧪 예시

상황: 대구 관광 콘텐츠 페이지에 날씨 API 키를 .env에 넣어 뒀어요.

git status 결과 보여주고, .env가 커밋 대상에 들어 있는지 알려줘.

결과: .gitignore에 .env가 적혀 있으면 바뀐 파일 목록에 .env가 아예 안 나와요. 목록에 보인다면 커밋하기 전에 막아야 한다는 신호예요.

📌 실수로 키를 올렸다면, 파일을 지우는 것보다 먼저 해당 서비스에서 키를 폐기하고 새로 발급하세요.

GitHub에서 Vercel까지: 배포 흐름

수업 후반에 만든 페이지를 Vercel로 배포해요. GitHub 저장소를 Vercel에 한 번 연결해 두면, 그 다음부터는 push만 해도 사이트가 자동으로 새로 만들어져요. 처음 연결은 이렇게 해요.

  1. vercel.com에서 Continue with GitHub로 가입해요.
  2. Add New → Project를 눌러요.
  3. 올릴 저장소 옆 Import를 누르고 Deploy를 눌러요.
  4. 1~2분 뒤 나오는 …vercel.app 주소가 내 사이트예요.
비유 GitHub는 원고를 넣는 우편함, Vercel은 우편함에 새 원고가 들어오는 순간 알림을 받고 바로 인쇄해 서점에 거는 출판사예요. 나는 원고만 넣으면 돼요.
📌 .env는 GitHub에 안 올라가니까 Vercel도 키를 몰라요. 내 컴퓨터에선 잘 되던 사이트가 배포 후 깨진다면 대개 이 이유예요. Vercel 프로젝트의 Settings → Environment Variables에 같은 이름과 값을 직접 넣어 줘야 해요. 환경 변수도 서버 쪽 코드에서만 읽어야 안전해요.
🧪 예시

상황: Vercel에 연결해 둔 대구 로컬 카페 랜딩페이지의 메인 문구를 바꾸고 싶어요.

메인 문구를 "대구의 아침, 한 잔의 커피"로 바꾸고 커밋하고 push해줘.

결과: push가 끝나고 잠시 뒤 Vercel 공개 URL을 새로고침하면 바뀐 문구가 보여요. Vercel 사이트에 따로 들어가서 버튼을 누를 필요는 없어요.

Claude Code로 말로 하는 Git

Git 명령어를 몰라도 괜찮아요. Claude Code가 터미널 명령을 대신 실행해 주니까 하고 싶은 일을 말로 설명하면 돼요. 다만 무엇을 했는지 결과 설명은 꼭 읽어 보세요.

하고 싶은 일이렇게 말해 보세요
처음 Git 시작"이 폴더를 Git 저장소로 만들고 .gitignore도 만들어줘"
세이브하기"지금까지 작업 커밋해줘. 메시지는 변경 내용 요약으로"
뭐가 바뀌었나 보기"마지막 커밋 이후 바뀐 내용 쉽게 설명해줘"
GitHub에 처음 올리기"GitHub에 새 비공개 저장소 만들고 올려줘"
이후 올리기"커밋하고 push해줘"
실험용 줄기"맛집 지도 작업용 브랜치 만들어서 거기서 작업해줘"
되돌리기"어제 커밋 상태로 되돌리고 싶어. 어떤 방법이 안전한지 먼저 설명해줘"
⚠️ "GitHub에 새 저장소 만들어줘"가 되려면 준비가 필요해요. 먼저 github.com에서 무료 계정을 만들어 두세요. 그다음 컴퓨터에 Git과 GitHub CLI(gh)를 설치하고, 터미널에서 gh auth login으로 GitHub 로그인을 한 번 해 둬야 해요. 설치나 로그인이 안 돼 있으면 Claude에게 "gh 설치하고 로그인하는 방법 단계별로 알려줘"라고 물어보세요.
💡 되돌리기, 강제 push처럼 기록을 지울 수 있는 작업은 바로 시키지 말고 "먼저 설명해줘"를 붙이세요. 확인하고 나서 진행해도 늦지 않아요.
🧪 예시

상황: 올리브영 마케팅 카드뉴스 HTML을 세 장 만들고 세이브하려고 해요.

지금까지 작업 커밋해줘. 메시지는 변경 내용 요약으로.

결과: Claude가 git add, git commit 같은 명령을 실행하고 "카드뉴스 1~3장 추가" 같은 메시지로 저장했다고 알려 줘요. 권한 모드에 따라 실행 전에 허락을 물으면 명령을 읽어 보고 허용하면 돼요.

터미널이 무섭다면: GitHub Desktop

버튼으로 Git을 쓰고 싶다면 GitHub Desktop ↗도 좋아요. 바뀐 파일 목록을 눈으로 보고, 커밋 메모를 적고, Push 버튼을 누르는 식이에요. Claude Code로 작업하고 GitHub Desktop으로 확인하는 조합도 초보에게 편해요.

🧪 예시

상황: Claude Code가 팀 피치덱 파일을 고쳤는데, 정확히 어디가 바뀌었는지 눈으로 보고 싶어요.

아직 커밋하지 말고 그대로 둬. 내가 GitHub Desktop에서 먼저 확인할게.

결과: GitHub Desktop의 Changes 탭에 바뀐 파일 목록이 뜨고, 지운 줄은 빨간색, 추가한 줄은 초록색으로 보여요. 확인한 뒤 거기서 바로 커밋해도 돼요.

매일 작업 루틴 체크리스트

  1. 시작할 때 다른 컴퓨터나 팀원이 바꾼 게 있다면 "최신 내용 pull해줘"
  2. 작업 중 의미 있는 단위가 끝날 때마다 "지금까지 커밋해줘" (예: 헤더 완성, 상품 표 추가)
  3. 위험한 실험 전 커밋 먼저, 또는 브랜치 만들기
  4. 올리기 전 ".env나 키가 섞여 있지 않은지 확인해줘"
  5. 끝낼 때 "커밋하고 push해줘" 후 Vercel 공개 URL에서 결과 확인

이 순서대로 저녁에 40분만 손봐도 세이브 포인트가 두세 개 생기고, GitHub와 Vercel 사이트가 오늘 작업으로 바뀌어 있어요. 내일 상품 표가 망가져도 헤더 완성 시점으로 돌아갈 수 있어요.

더 알아보기

좋은 커밋 메시지는 "무엇을, 왜" 바꿨는지 한 줄로 적은 거예요. "수정"보다 "올리브영 기획안 가격표 2026 기준으로 갱신"이 나중에 찾기 훨씬 쉬워요. CLAUDE.md에 "커밋 메시지는 무엇을 왜 바꿨는지 보이게 쓴다"라고 한 줄 적어 두면 매번 말하지 않아도 돼요.
